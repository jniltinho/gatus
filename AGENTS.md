# AGENTS.md

Guidance for AI coding agents working in this repository.

> **`jniltinho/gatus`:** also read [AGENTS.fork.md](AGENTS.fork.md). Its rules complement this file and take precedence when they conflict.

## Commands

- `make install` — Build the `gatus` binary
- `make run` — Run in dev mode (uses `./config.yaml`)
- `make test` — Run all Go tests with coverage
- `make clean` — Remove built binary
- `make frontend-install` — Install frontend npm dependencies
- `make frontend-build` — Build the Vue.js frontend (**must run after any `web/` changes**)
- `make frontend-dev` — Start the Vue dev server

## Key Rules

- **Dependencies**: After adding/updating a Go dependency, run `go mod tidy` (`vendor/` is not used)
- **Frontend build artifacts**: `web/static/` is generated by `make frontend-build` and embedded into the Go binary at compile time via `//go:embed`. Never edit files in `web/static/` directly
- **Config validation order**: In `internal/config/config.go` `parseAndValidateConfigBytes`, `ValidateAlertingConfig` **must** run before `ValidateEndpointsConfig` because provider default alerts must be parsed before endpoint defaults are set
- **Invalid configs are fatal at startup** — `gatus` exits with `Error:` and status 1, and `gatus config validate` must catch the same problems: whatever can make the server fail to start (a password that is not a bcrypt hash, for example) belongs in the validation, not in the start
- **Hot-reload**: `cmd/serve.go` watches the config file and re-runs the full stop → save → load → init → start cycle. New startup logic must account for this

## Environment Variables

- `GATUS_CONFIG_PATH` — Config file path (default: `config/config.yaml`); can be a directory of YAML files (deep-merged)
- `GATUS_LOG_LEVEL` — `DEBUG`, `INFO`, `WARN`, `ERROR`
- `ENVIRONMENT=dev` — Enables CORS for frontend dev on `localhost:8081`

## Project Structure

- `main.go` — Entry point; only calls `cmd.Execute()`
- `cmd/` — Cobra commands (`serve`, `version`, `config validate`, `password hash`, `healthcheck`); `serve` loads config, initializes storage, starts watchdog + API server
- `internal/config/` — Central config struct (`config.go`) and sub-packages per config section (each with `ValidateAndSetDefaults()`)
- `internal/alerting/` — Alerting config (`config.go`), alert types (`alert/type.go`), and one sub-package per provider under `provider/`
- `internal/api/` — Echo v5 HTTP API routes and SPA serving
- `internal/httpx/` — The only place that knows Echo's request/response quirks; handlers read and write through it
- `internal/watchdog/` — Monitoring loop; spawns a goroutine per endpoint with semaphore-based concurrency control
- `internal/client/` — HTTP/gRPC client used for health checks
- `internal/storage/store/` — Storage abstraction with `memory/`, `sql/` (SQLite, PostgreSQL, MySQL/MariaDB) implementations
- `internal/security/` — Authentication (basic + OIDC) and security middleware
- `web/app/` — Vue 3 frontend source; builds to `web/static/` (embedded into the Go binary)
- `third_party/` — Local copies of the TwiN modules, wired by `replace` in `go.mod`

## Common Changes

### Adding an Alerting Provider

Use `internal/alerting/provider/slack/` as the reference implementation. Every new provider touches **6 locations**:

1. **Create provider package** — `internal/alerting/provider/{name}/{name}.go` + `{name}_test.go`
   - `Config` struct with `Validate()` and `Merge(*Config)` methods
   - `AlertProvider` struct with `DefaultConfig` (yaml inline), `DefaultAlert *alert.Alert`, `Overrides []Override`
   - Use `client.GetHTTPClient(nil)` (not `http.DefaultClient`), always `defer response.Body.Close()`
2. **Register type** — Add `Type{Name} Type = "{name}"` in `internal/alerting/alert/type.go`
3. **Add to config struct** — Add field to `alerting.Config` in `internal/alerting/config.go`; the **YAML tag must exactly match** the `alert.Type` string (reflection-based lookup via `GetAlertingProviderByAlertType`)
4. **Add compile-time checks** — Both `_ AlertProvider = (*pkg.AlertProvider)(nil)` **and** `_ Config[pkg.Config] = (*pkg.Config)(nil)` in `internal/alerting/provider/provider.go`
5. **Register in validation** — Add the type to the `alertTypes` slice in `internal/config/config.go` `ValidateAlertingConfig`
6. **Document** — Add to README.md in alphabetical order

### Adding a Config Section

1. Create package in `internal/config/` with struct + `ValidateAndSetDefaults()` method
2. Add field to `Config` struct in `internal/config/config.go`
3. Add `Validate*` call in `parseAndValidateConfigBytes` — **respect ordering constraints** (see comments in that function)

## Frontend

- Vue 3 Composition API (`<script setup>`) + Tailwind CSS
- Props-based data flow — **do not use provide/inject**
- All components must include `dark:` prefixed Tailwind classes for dark mode
- `window.config` contains server-injected UI settings (Go template placeholders)

## API Routes (`internal/api/api.go`)

- Two groups under `/api`: the public one and the protected one, which carries the security middleware
- Protection comes from the group a route is registered on, not from the order of the registrations

## Testing

- Config structs should have `*_test.go` files
- Use `t.Parallel()` where appropriate
- API tests spin up test servers (see existing `*_test.go` in `internal/api/`)

## Commits & PRs

When creating a commit or PR as an agent, state that it was made by an agent and include your model name and version.
